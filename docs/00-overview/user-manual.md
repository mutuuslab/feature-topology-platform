# 사용자 설명서 — 역할별 업무

> 대상: 고객사에서 Feature Platform을 쓰는 사람(Feature 설계·승인·품질·운영·감사 담당). 설치·운영은 `docs/20-architecture/20-91-install-guide.md`.
> 화면 이름은 왼쪽 메뉴에 보이는 이름 그대로 적는다. 화면마다 머리의 **핵심 메시지** 한 줄이 "지금 무엇을 해야 하는지"를 말하고, 그 옆 행동 버튼이 다음 할 일로 데려간다.

## 1. 시작하기

### 1.1 로그인

1. 회사가 알려 준 주소(예: `https://ff.oem.example`)로 들어가 **회사 계정(SSO)으로 로그인**을 누른다.
2. 회사 로그인 화면(사내 계정·다단계 인증)을 마치면 플랫폼으로 돌아온다. 로그인 전에 열려던 화면이 있으면 그 화면으로 돌아온다.
3. 오른쪽 위에 내 이름과 **역할**이 보인다. 역할은 회사 계정의 그룹에서 정해진다 — 필요한 역할이 없으면 IT·권한 담당자에게 그룹을 요청한다.
4. 일을 마치면 오른쪽 위 메뉴의 **로그아웃**. 오래 손대지 않으면(기본 60분) 세션이 끝나고, 다음 동작 때 다시 로그인 화면으로 간다.

### 1.2 역할 고르기

한 사람이 여러 역할을 받았으면 위쪽 역할 선택기에서 **지금 맡을 역할**을 고른다. 화면의 버튼은 고른 역할이 할 수 있는 일만 켜진다(잠긴 버튼에 마우스를 올리면 필요한 역할이 보인다).

직무 분리 규칙 때문에 같은 사람이 이어서 할 수 없는 일이 있다 — 예: 자기가 작성한 Feature를 승인, 긴급 차단을 승인한 사람이 그 차단의 복원도 승인. 이런 시도는 거부되고 감사 이력에 남는다.

### 1.3 화면 읽는 법

| 요소 | 뜻 |
|---|---|
| 핵심 메시지(머리 한 줄) | 이 화면에서 지금 중요한 한 가지 — 숫자·상태와 다음 행동 |
| 빈 상태 안내 | 아직 기록이 없을 때. 설치 직후에는 대부분의 화면이 "아직 등록된 Feature가 없습니다"처럼 보이고, 다음 할 일(예: Feature 제안하기)로 가는 링크가 있다 |
| 오류 안내 | 불러오지 못했을 때 — **다시 시도**. 반복되면 안내에 나온 상관 ID를 운영 담당자에게 알린다 |
| 저장하지 않은 변경 | 입력 중에 화면을 떠나려 하면 묻는다 |
| 업무 절차(오른쪽 위 "이 화면의 업무 절차") | 이 화면이 속한 표준 절차와 내 차례 |

| 메뉴 묶음 | 화면 |
|---|---|

| Feature 정의 | Feature 제안 · Feature Registry · Feature 등록 · 변경요청 · Taxonomy |

| 기준정보 | UPG·UPG-VC · SW·Artifact · SW 구조 · SW EO · 제어점 · 데이터 사전점검 |
| 검증·Gate | 품질 기준·Evidence · 분야별 검증 이력 · 컴플라이언스 · 품질 피드백 · CARLA 가상검증 · 실험·효과 · 요구·안전 추적 |
| 상품·출시 | Feature Catalog 상품 · 사용 권한·체험권 · 활성화 판단 · 정책·검증·승인 · Flag Retirement · 서명 배포·차량 회신 |

어느 화면에서든 `⌘K`(Windows `Ctrl+K`) 검색으로 화면 이름이나 Feature ID를 찾아 바로 간다.

## 2. 큰 흐름 — Feature 하나가 차량에 닿기까지

```
Feature 제안 → (승인) → Gate 판정·안전 분류 확정 → Baseline 확정 → 상품 구성 → 정책 작성·검증 8종·승인
→ 서명 배포 → 차량 회신 확인 → 운행 중 감시 → (필요하면) 긴급 차단·롤백 → Flag Retirement
```

각 단계는 맡은 역할이 다르고, 넘어갈 때마다 **다른 사람의 승인**과 **감사 기록**이 남는다. 내 차례인 일은 **홈 → 검토함**과 **업무 절차**에 모인다.

## 3. 역할별 업무

### 3.1 Feature 설계(Feature 작성자)

- **Feature 제안**: 이름·설명·요구 ID·국가·차종·트림·담당자·ASIL·UPG-VC·제어점(Flag·Parameter·Signal·DTC)을 적고 **등록**하면 `PROPOSED 0.1.0`이 생긴다. 같은 국가·차종·트림에 이름이 비슷한 Feature가 있으면 등록 대신 기존 Feature를 보여 준다 — 새 Version인지 먼저 확인한다.
- **Feature Registry**: 모든 Feature·Version의 원장. 상세에서 Lifecycle·Gate·의존관계·안전 분류·이력을 본다.
- **Feature 등록**: 아직 출시 전인 내 Feature들과 다음 할 일.
- **새 Version**: 승인된 뒤의 속성 변경은 모두 새 Version으로 만든다(국가·차종·트림을 바꾸려면 새 Feature).
- **Release Sign-off**: G8·G9가 통과한 뒤 Feature Owner가 출시 책임을 개인 서명으로 확인한다.

### 3.2 구성 승인(Feature 승인자·상품 승인자)

- **검토함**에서 승인 요청을 열어 근거(요구·Gate·영향)를 보고 승인 또는 반려(사유 필수)한다.
- **BOM 기준선·확정 승인**: APPROVED Version을 불변 Baseline으로 고정한다 — 요청자와 승인자는 다른 사람이어야 한다.
- **Feature Catalog 상품**: 확정 Baseline으로 상품을 구성하고 출시를 승인한다.

### 3.3 품질 검토(Gate 판정자·기능안전 담당자 FSM)

- **품질 기준·Evidence**: Gate마다 필요한 근거와 제출 상태.
- Feature 상세의 **안전 분류**: F·DC·R 등급과 시간값을 검토해 개인 서명으로 확정한다(G2 선행 조건).
- **분야별 검증 이력**·**CARLA 가상검증**: 정책별 검증 결과, 가상 차량 재현 근거(G5).
- **요구·안전 추적**: 요구 → 구현 → 검증의 빈 곳(요구 없음·구현 없음·근거 없는 PASS·미확정 안전 분류).
- **긴급 차단 승인**: 운영자가 요청한 차단을 안전 관점에서 승인한다(2인 승인 중 한 칸).

### 3.4 PLM 기준정보(BOM 승인자·Variant 담당자·법규 담당)

- **기준정보** 메뉴: UPG·UPG-VC, SW·Artifact, SW 구조, SW EO, 제어점을 관리한다.
- **데이터 사전점검**: 원본 데이터 오류를 지우지 않고 경고로 보여 준다 — 출시 전에 정리한다.
- **Variant·지원 조건**: 이 Version을 실행할 수 있는 차량 사양·SW 조건을 Fleet에 대 본다.
- **컴플라이언스**: 시장별 법규 Profile과 게이트 사전 판정.

### 3.5 상품 권리(상품 작성자)

- **사용 권한·체험권**: 구독·구매·체험 권한. 체험은 수락한 날부터 30일 켜진다.
- **체험 전환 분석**: 제안 → 수락 → 구매 전환을 성향별로 본다(5대 미만 집단은 가린다).

### 3.6 정책·출시(구현 담당자·Feature 출시 담당자)

- **정책·검증·승인**: Control Point별 활성화 정책을 작성(DRAFT)하고 검증 8종을 돌린 뒤 다른 사람의 승인을 받는다. 개정본마다 전체가 남고, 이전 버전으로 되살리면 DRAFT로 돌아가 검증·승인을 다시 받는다.
- **활성화 판단**: 이 차량에서 이 flag가 켜지는지 서버 기준 7단계(배포·차단·적용 범위·권한·대상·코호트·결정)로 본다.
- **서명 배포·차량 회신**: 서명된 게시본이 차량에 닿았는지 회신으로 확인한다.
- **Flag Retirement**: 다 쓴 Flag를 절차대로 거둔다.

### 3.7 차량 운영(운영자·운영 리더)

- **Fleet 실시간 적용 현황**·**차량별 적용 상태**·**전세계 차량 지도**: 배포·차단이 차량에 실제로 적용됐는지, 차량 판단이 서버 판단과 같은지.
- **긴급 차단·복구**: 안전·보안 사유로 기능을 끈다. **긴급 차단 요청** → 대상 Feature·차량·사유 분류·봉쇄 근거를 적고, 확인 창에 Feature ID를 직접 입력해 요청한다 → 기능안전 담당자와 운영 리더가 승인하면 서명된 차단 명령이 나간다 → 차량 회신(CONFIRMED)을 확인한다. 복원은 차단을 승인한 사람과 **다른 두 사람**이 승인한다.
- **롤백**: 배포된 정책을 이전 버전으로 되돌린다 — 실행은 승인 뒤에만.
- **이상 징후 대응**: 차량 고장·서명 거부·회신 이상을 Feature별로 묶은 권고(차단·검토·무시).
- **운행 중 감시 지표**·**장애·VOC**·**운영 데이터·이벤트**: 출시된 Version의 운행 중 안전 지표와 경보, 고객 불만·장애, 차량이 보낸 보고와 회신.

### 3.8 시스템 연계·사이버보안(구현 담당자·사이버보안 담당자 CSM)

- **외부 연계 현황**: 각 연계(IF)의 연결 방식(실제·모의·꺼짐)과 최근 호출.
- **데이터 동기화**: GitLab·JIRA·codeBeamer와의 양방향 동기화, 충돌 해결.
- **OpenFeature 범위**: 앱 SDK가 받은 값이 서버 판단과 같은지.
- **보안·인증서**: 서명 키·인증서·SBOM·취약점(VEX)·보안 이벤트. 복원 승인 칸 중 하나를 맡는다.

### 3.9 협의와 개발 이관(Feature 출시 담당자)

- **변경요청**: 변경 요청과 Version 이력, Baseline 비교.
- **협력사 이관**: 협력사 SW 납품과 이관 상태.

### 3.10 조회·감사(운영·감사 조회자)

- **감사 이력**: 모든 등록·변경·승인·거부·실패 기록. 추가만 되고(수정·삭제 불가) 해시 체인으로 위변조를 검출한다 — 머리의 체인 검증이 정상인지 본다.
- **감독 기록**·**플랫폼 인증·권한**: 역할별 권한, 직무 분리 규칙, 최근 거부 시도와 겸직 계정.
- **데이터·규제 기록**: 기록 종류별 보존 기간과 삭제 기록, 데이터 접근 요청.

## 4. 자주 하는 일

| 하고 싶은 일 | 어디서 |
|---|---|
| 내 차례인 일 보기 | 홈 → 검토함 / 업무 절차 |
| 새 기능 등록 | Feature 정의 → Feature 제안 |
| 이 Feature를 바꾸면 어디가 흔들리나 | 구성·Topology → 변경 영향 분석 |
| 이 차량에서 기능이 왜 꺼져 있나 | 상품·출시 → 활성화 판단(차량·flag 고르기) |
| 배포가 차량에 닿았나 | 상품·출시 → 서명 배포·차량 회신 / 차량 운영·안전 → Fleet 실시간 적용 현황 |
| 기능을 지금 당장 꺼야 한다 | 차량 운영·안전 → 긴급 차단·복구 → 긴급 차단 요청 |
| 누가 언제 무엇을 바꿨나 | 연계·감사·관리 → 감사 이력(대상·행위자·결과로 거르기) |
| 알림을 메일로도 받기 | 홈 → 알림 → 받는 방법(승인 요청·긴급 차단은 끌 수 없다) |

## 5. 표준 따라하기

**홈 → 표준 따라하기**는 표준 보고서 케이스를 실제 화면에서 단계별로 따라 하며 규칙이 어디서 동작하는지 보는 학습 화면이다. 시나리오의 Feature·차량 ID는 예시 데이터(데이터셋 v0.81) 기준이라, 예시 데이터가 없는 운영 설치에서는 화면이 그 사실을 먼저 알리고 단계 설명만 읽을 수 있다. 실제로 따라 하려면 예시 데이터를 넣은 연습용 설치를 쓴다.

## 6. 문제가 생기면

| 증상 | 할 일 |
|---|---|
| 회사 로그인은 됐는데 플랫폼이 로그인을 거부한다 | 회사 계정에 플랫폼 역할로 이어지는 그룹이 없다 — 권한 담당자에게 그룹 요청 |
| 버튼이 잠겨 있다 | 역할 선택기에서 그 일을 할 역할을 고른다. 없으면 권한 요청 |
| "이 역할로는 볼 수 없습니다" | 다른 역할이 볼 화면이다 |
| 저장했는데 충돌 안내가 나온다(다른 사람이 먼저 바꿈) | 화면을 새로 고쳐 최신 내용을 보고 다시 한다 |
| "요청이 너무 잦습니다" | 안내된 초만큼 기다린다 |
| 계속 "불러오지 못했습니다" | 오류 안내의 상관 ID와 시각을 운영 담당자에게 알린다(운영 담당자는 로그·감사 이력에서 같은 ID를 찾는다) |
