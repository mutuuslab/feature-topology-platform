## 3. 고친 것

| 문제(측정) | 원인 | 고침 |
|---|---|---|
| Feature 목록 2 s | 버전마다 Gate 기록을 따로 조회(N+1)·요약을 페이지 전체가 아니라 전부 만든 뒤 자름·매 요청 2천여 문서 파싱과 `localeCompare` 정렬 | 거른 뒤 페이지만 요약, Gate 상태는 한 질의(`GateRepo.latestStatuses`, 문서 없이 네 열), Feature 문서·Gate 상태 표는 쓰기 때까지 캐시(트랜잭션 안에서는 만들지 않음, 캐시 행은 freeze) |
| 최근 활동 12 s | `at >= ?`에 색인 없음 — 이벤트 50만·감사 100만을 매번 통째로 | 마이그레이션 070 `events_at`·`audit_at`(덮는 색인), 이벤트는 플래너가 GROUP BY 색인을 고르지 않게 `INDEXED BY events_at` |
| 차량 가젯 10 s(24 MiB) | 가젯이 차량 수를 세려고 전체 목록을 받음 | `/api/vehicles`에 `limit`·`cursor`(VIN 순)·`total`·`sample`(뒤 호환), 가젯은 `limit=1`로 수만. 표본 수는 식 색인 `vehicle_fleet`으로 센다 |
| 내 알림 17 s | 볼 수 있는 알림 전부를 읽어 JSON으로 풀고 JS에서 세고 자름 | 안 읽음 수·범주 집계는 SQL(수신자 색인 IN), 본문은 limit건만, 집계는 알림·읽음이 바뀔 때까지 캐시. 알림 번호는 `count(*)` 대신 `max(rowid)`(추가만 하는 표) |
| 긴급 차단 요청 1.1 s | 영향 범위가 차량 10만 대 문서를 모두 읽어 거르고, 대상 차량마다 다시 전체 목록에서 시장을 찾음 | 차량 지정 시 그 VIN만, 아니면 식 색인 `vehicle_scope`(국가·차종·트림)로 SQL 선택, 진행 중 차단은 Feature 기준(`kill_request_feature`), 시장은 한 번의 VIN 조회 |
| OFREP·GLEO 가명 조회 | 요청마다 전 차량의 가명(SHA-256)을 계산 | 가명 → VIN 표(차량이 늘 때만 다시 만듦) |
| 부팅 때 감사 전체 훑기 | `hash IS NULL` 찾기에 색인 없음 | 부분 색인 `audit_unhashed`(평소엔 빈 색인) |
| 감사 체인 검증 32 s 막힘 | 100만 행을 한 번에 읽고 해시 | HTTP 창구는 묶음 검증(`verifyChainAsync`, 묶음 사이 `setImmediate`), 동시 호출은 진행 중인 검증 하나를 함께 기다림. 동기 `verifyChain`(시험·5년 재생)은 그대로 |
| 큰 DB에서 흩어진 행 읽기가 디스크로 | 기본 페이지 캐시 2 MiB — 대상별 이벤트·감사 조회가 바쁜 기계에서 p95 수백 ms~1.7 s로 흔들림 | `PRAGMA cache_size`(64 MiB)·`mmap_size`(256 MiB) — 읽기만, 쓰기·내구성(`synchronous`) 설정은 그대로 |
| 그 밖의 전체 차량 읽기 | 롤백 DTC 조건·Data Act 요청·5년 재생 표본 수가 한 대를 찾으려고 전체 목록 | VIN 직접 조회·색인 개수 세기 |

## 4. 동기 SQLite — 남은 한계

`node:sqlite`는 동기 API라 질의·JSON 처리 시간만큼 이벤트 루프가 막히고, 그동안 다른 요청(차량 채널 포함)은 기다린다. 쓰기는 `BEGIN IMMEDIATE`로 한 줄로 선다.
위 수정으로 주요 API의 막힘은 대부분 100 ms 아래가 됐지만 다음은 남는다 — 근본 해결은 PostgreSQL 전환(별도 작업)과 무거운 집계의 비동기화다.

| 남은 것 | 크기(full) | 비고 |
|---|---|---|
| 안전 분류 목록 `/api/safety-profiles` | 1.6 MiB, 한 요청 약 0.35 s 막힘 | 버전 2천여 개 전체 문서. 대시보드 목록이 필요한 항목만 받도록(페이지·요약) 바꿔야 한다 |
| Feature 최신 버전 전체(`latestOnly=true`) | 711 KiB, 약 0.2 s | 대시보드·홈이 전체를 받는다. 쪽 나눔은 화면 쪽 작업 |
| 전체 차량 목록 `/api/vehicles`(limit 없음) | 24 MiB, 약 1 s | 대시보드는 고쳤지만 차량 고르기 화면(체험권·운영·런타임)은 아직 전체를 받는다 — 검색형 선택기로 바꿔야 한다 |
| 알림 안 읽음 수(캐시가 비었을 때) | 볼 수 있는 알림 5만 건이면 약 0.3 s | 볼 수 있는 알림 수에 비례. 새 알림·읽음마다 캐시가 비워진다. 계정별 안 읽음 계수표나 오래된 알림 자동 읽음(사용자 결정)이 필요하다 |
| 감사 체인 전체 검증 | 100만 행 약 37 s(막힘은 묶음당 수십 ms) | 판정을 약하게 하지 않으려고 증분 검증은 하지 않았다 |
| 부팅 시간 | 약 7~9 s | 대부분 Windows 모듈 적재(파일 stat) — DB 크기와 무관. 부팅 예산 30 s |
| 캐시 전제 | — | Feature·Gate·알림 집계·가명 표 캐시는 프로세스 안 — 한 설치 = 한 백엔드 프로세스(SQLite 단일 쓰기) 전제. 여러 프로세스로 늘리면(PostgreSQL 전환 때) 캐시를 다시 설계해야 한다 |

## 5. 돌리는 법

```bash
cd FF
node tools/load/run.ts --profile light --md      # 기본 verify와 같은 것
node tools/load/run.ts --profile full --md       # 첫 실행은 시드(2~4분)
node tools/load/run.ts --profile full --only notifications,kill.issue
node tools/load/seed.ts --profile full --force   # 시드 DB 다시 만들기
```

예산을 올릴 때는 `harness/perf-budgets.json`의 note에 이유를 남긴다. 새 시나리오는 예산이 없으면 실패한다(`tools/load/stats.test.ts`).
