# 20-92 PostgreSQL 이전 설계 — 단계·하네스·위험 (D-RD-3)

> 결정 D-RD-3(사용자): **PostgreSQL로 이전**. 이 문서가 이전의 정본이다 — 출시 준비 항목 RD-OPS-14(`20-90` §2)·설치 안내서 `20-91` §6.1·§6.2와 짝.
> 진행 상태는 `FF/PROGRESS.md`, 호환 측정은 `FF/harness/pg-compat.json`(`npm run test:pg`가 쓴다).
> 작성 2026-10-25 · 1단계 구현 브랜치 `feat/postgres-phase1`.

## 1. 한 줄 요약

**SQL을 고치지 않고 PG 어댑터가 실행 직전에 번역**하고(방언 번역기), **동기 Db 계약은 워커 스레드 다리로 그대로** 둔 채,
**같은 백엔드 시험 묶음을 PostgreSQL 16에서 돌려 통과 수를 래칫**으로 잡는다. 그 위에서 호출부를 하나씩 비동기 Db로 옮기고(2단계),
프로세스 메모리 상태를 DB 공유 상태로 옮긴 뒤(3단계) 인스턴스를 늘린다. 1단계 측정: **백엔드 시험 769/775가 PostgreSQL 16에서 통과, 실패 0**(§6).

## 3. 메모리 상태 → 공유 상태

공통 인터페이스 `SharedStateStore`(`backend/src/kernel/shared-state.ts`, 공급자 `SHARED_STATE`) — DB 구현 하나가 SQLite 파일·PostgreSQL 양쪽에서 같다.

- **예약** `reserve(slot, value, ttl)` / `release(slot)` — 만료 행을 지운 뒤 원자적 삽입(`INSERT OR IGNORE` = `ON CONFLICT DO NOTHING`). 기본 키 충돌이면 남의 것이고 그 값(본문 해시)을 돌려준다.
  만료는 벽시계(주인이 죽어도 10분 뒤 풀림). 멱등 인터셉터는 예약 뒤 저장 응답을 **한 번 더** 본다(다른 인스턴스가 끝내고 풀었을 수 있다).
- **창 카운터** `hit(key, window, now)` — `INSERT … ON CONFLICT DO UPDATE SET n = CASE …, start_ms = CASE … RETURNING` 한 문(경쟁 없음).
- **임대** `instance-lease.ts` — 부팅 때(마이그레이션 **전**) 잡고, 부팅 중 기한 2분 → 부팅 끝에 보통 기한(20초)으로 줄이고 1/3마다 갱신(비동기 Db 첫 사용처), 종료 때 놓는다.
  같은 호스트에서 주인 PID가 이미 없으면 바로 넘겨받는다(컨테이너 재시작). 백업 사본에서는 임대·예약 행을 지운다.
- 3단계 설계(아직 없음):
  - **SSE** — `EventService.publish`가 같은 tx에서 `pg_notify('ff_events', seq)`. 인스턴스마다 LISTEN 연결 하나(풀 밖), 알림을 받으면 `events`에서 `seq > 마지막` 을 읽어 Subject로. 놓친 알림은 SSE 재접속의 `?after=seq`가 메운다(지금 계약 그대로).
  - **예약 작업** — `scheduled_task(due_at, kind, payload, claimed_by, claimed_until)` 표. 지도자 임대(`instance_lease` 이름 `scheduler`)를 쥔 인스턴스만 `FOR UPDATE SKIP LOCKED`로 가져가 실행. 시험의 `FF_SCHEDULER=manual`은 같은 표를 수동으로 비운다.
  - **감사 추가** — `pg_advisory_xact_lock(감사)`로 추가를 직렬화하고 끝(id·hash)을 그 tx 안에서 읽는다. 프로세스 기억 대신 DB 끝 + DB 밖 고정점.
  - 그 뒤에야 `FF_INSTANCE_LOCK=off`(지금은 검증용·운영 거부)를 운영에서 허용한다.

## 4. 목표 구조

### 4.1 1단계 — 동기 다리 (`pg-sync-db.ts`)

- 워커 스레드 하나가 `pg` 연결들을 들고, 주 스레드는 `SharedArrayBuffer` + `Atomics.wait`로 결과를 기다린다(`receiveMessageOnPort`). **동기 Db 계약이 그대로**라 코드 수백 곳을 바꾸지 않고 PG에서 돈다.
- 비용: 질의마다 주 스레드를 막는다(node:sqlite도 동기라 성격은 같고 **왕복 지연만 더해진다**). Windows Docker Desktop 포트 전달에서 왕복 약 2~3 ms, 데모 데이터 부팅 3,643 왕복 ≈ 10초(SQLite 1초 안).
- 트랜잭션: 연결 하나에서 `BEGIN`/`SAVEPOINT`, 커밋 뒤 `afterCommit` — SQLite 구현과 같은 규칙. 연결마다 `search_path`·`lock_timeout 15s`·UTC.
- 문장 보호(선택 `FF_PG_STATEMENT_GUARD=1`): PG는 tx 안 한 문이 실패하면 tx 전체가 중단된다(SQLite는 아니다). 켜면 문마다 SAVEPOINT(왕복 3배). 기본 끔 — 시험 묶음에서 이 차이로 실패한 시험은 없었다.
- 정수: `int8`·`numeric`을 JS number로(2^53 넘는 값은 없다 — 시각 ms·순번).

### 4.2 2단계 목표 — 비동기 Db (`async-db.ts`)

```ts
interface AsyncDb { run/get/all(sql, ...p): Promise<…>; tx<T>(fn: (t) => Promise<T>): Promise<T>; close(); dialect }
```

- `PgPoolDb`(pg.Pool, tx = 연결 하나 빌려 BEGIN…COMMIT — await 사이에 다른 요청이 끼지 않는다), `SqliteAsyncDb`(동기 SQLite를 감싸고 tx는 뮤텍스로 순서대로, 파일 DB는 전용 연결).
- SQL 방언은 동기 Db와 같다(SQLite 방언 + 번역). **1단계에서 계약·두 구현·계약 시험(`db-adapters.spec.ts`, SQLite·PG 양쪽)과 첫 사용처(임대 갱신)를 넣었다.**
- 옮기는 순서: ① 커널 배경 작업(임대·정리·고정점·이벤트 조회) ② 어댑터(OTA·외부 연계·Unleash — 이미 async 함수) ③ 요청 경로를 컴포넌트 단위로(조회 → 상태 전이). 컴포넌트 하나를 옮길 때 그 컴포넌트의 tx 전체를 함께 옮긴다(동기 tx와 비동기 tx가 같은 행을 두고 섞이면 교착 — 다리 연결과 풀 연결은 서로 다른 세션).
- 래칫(2단계에 추가): "동기 Db 호출 수"는 줄어들기만 한다. 0이 되면 다리를 지운다.

### 4.3 방언 — 번역기 + 마이그레이션별 덮어쓰기 (`pg-dialect.ts`)

- §2.2 표의 규칙을 **한 곳**에서 적용한다. 문자열 리터럴·따옴표 이름·주석은 가린 뒤 바꾸고 되돌린다(문자열 안의 `?`·`LIKE`는 그대로).
- 번역 문맥은 마이그레이션을 훑어 만든다: 표의 정수 키(RETURNING·rowid 대상), 트리거의 표(DROP TRIGGER).
- 번역기가 못 하는 마이그레이션은 **같은 항목에 `pg` 필드**로 PG SQL을 따로 둔다(`{ name, sql, pg? }`). 잠금은 `sql`만 해시하므로 기존 마이그레이션 잠금을 깨지 않는다. 지금 덮어쓰기는 0건 — 42건 모두 번역된다(`pg-dialect.spec.ts`가 확인).
- 마이그레이션 실행기는 같다(`migrate()` — `schema_migrations`, 이름 순, 건마다 tx). PG는 DDL도 트랜잭션이라 실패한 마이그레이션이 반쯤 남지 않는다.
- 정렬: PG DB는 **C 정렬**(`--locale=C`)로 만든다 — SQLite의 이진 비교와 같은 순서.
- 방언을 PG 쪽으로 바꾸는 일(번역기 제거, `jsonb` 열)은 SQLite를 운영에서 내린 뒤(5단계).

### 5.1 데이터 이전 도구 (`backend/src/ops/sqlite-to-pg.ts`, 1단계 구현)

`node backend/dist/ops/sqlite-to-pg.js --from <ff.db> --to postgres://…` (앱을 멈춘 뒤)

1. 원본이 이 판의 마이그레이션을 **모두** 마쳤는지(아니면 먼저 SQLite로 한 번 부팅).
2. 대상이 **빈 DB**인지(덮어쓰지 않는다) → 대상에 같은 마이그레이션 적용.
3. 표마다 행을 그대로 옮긴다 — 감사 id·해시·JSON 문자열을 바꾸지 않는다(해시가 저장 문자열에 묶여 있다). 실행 중 상태(임대·예약)는 뺀다. 한 tx.
4. 정수 키 순번을 옮긴 최대값 다음으로(`setval`).
5. **검증**: 표마다 행 수, 감사 체인을 **대상에서 처음부터 다시 계산**한 끝 해시 = 원본 끝 해시. 어긋나면 `ok:false`(대상을 버리고 원본으로 계속).
6. 앱을 PG로 띄워 `GET /api/audit/chain`(DB 밖 고정점 포함)이 `ok: true`. 시험 `sqlite-to-pg.spec.ts`가 이 전 과정을 PG에서 돈다(부팅·검증·이어 쓰기·순번).

되돌리기: 도구는 원본을 **읽기만** 한다 — `FF_DB_URL`을 지우면 원본으로 부팅. 이전 뒤 PG에서 생긴 변경은 SQLite로 되돌아가지 않는다(역방향 도구 없음 — 미리보기 기간에는 시험 설치에서만 쓴다).

## 6. 하네스 — PG 호환 래칫

## 7. 위험

| ID | 위험 | 지금 대응 | 남은 것 |
|---|---|---|---|
| R1 | 번역기(정규식)가 놓친 방언 차이가 숨는다 | 전체 시험 묶음을 PG에서 돌려 래칫, 번역 단위 시험 | 시험이 닿지 않는 SQL 경로 — 2단계에서 호출부를 옮기며 원문 확인 |
| R2 | 동기 다리가 주 스레드를 막는다(왕복 지연 × 질의 수) | 미리보기로만, 부팅 통계(`FF_PG_TRACE`) | 2단계 비동기 Db, 4단계 부하 시험 |
| R3 | NULL 정렬(SQLite ASC = NULL 먼저, PG = 나중) | 시험에서 드러난 실패 없음 | `ORDER BY` 의 NULL 열을 2단계에서 `NULLS FIRST`로 명시 |
| R4 | tx 안 한 문 실패 → PG는 tx 중단 | 실패를 잡아 계속하는 코드는 중첩 `tx()`(SAVEPOINT) 규칙, 선택 `FF_PG_STATEMENT_GUARD` | 2단계에서 그런 코드 목록화 |
| R5 | 형(型) 차이 — 정수 열에 소수, 문자열/정수 비교 느슨함 | `INTEGER→BIGINT`, int8→number | 실패 시험 0이지만 운영 데이터는 더 다양 — 이전 도구가 형 오류면 tx 전체 롤백 |
| R6 | 정렬 규칙 | C 정렬 DB 필수(설치 안내 §6.1) | 상태 점검이 정렬을 확인(2단계) |
| R7 | 다중 인스턴스에서 감사 체인 갈라짐·끝 오판 | 단일 인스턴스 임대 | 3단계 감사 추가 직렬화 |
| R8 | 봉인 전 평문 비밀의 잔재 — SQLite `secure_delete`, PG는 MVCC 옛 행이 VACUUM 전까지 남는다 | 이전 도구는 이미 봉인된 값을 옮긴다 | PG에서 첫 봉인 뒤 `VACUUM` 안내(2단계) |
| R9 | 이전 뒤 순번 겹침 | `setval` + 시험(이어 쓴 감사 id) | — |
| R10 | `LIKE`→`ILIKE` 비ASCII 대소문자(SQLite는 ASCII만 무시) | 한국어엔 대소문자가 없다 | — |
| R11 | Windows Docker Desktop 지연이 시험 시간 한도를 넘긴다 | `test:pg`는 시간 한도 180초 | CI(Linux)에서 돌릴 때 다시 잰다 |
