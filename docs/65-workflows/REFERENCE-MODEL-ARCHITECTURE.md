# 업무 레퍼런스 모델 설계

## 데이터 경계

기존 프로세스·활동·조직 역할·WP를 유지하고 **업무를 어떻게 정의하는지**를 BP 층으로 보강한다. BP는 실행 이력 ID를 대체하지 않는다. 한 BP가 연결한 활동의 실제 진행과 BP/성과 정의는 별개다. 현재 정의가 플랫폼에서 자동 수행되는지, 외부 조직에서 수행하는지는 기존 platform.actions/screens와 명시적 참고로 설명한다.

```yaml
process:
  id: FPW.1
  # 기존 purpose_ko/outcomes/activities/work_products 유지
  base_practices:
    - id: FPW.1.BP1
      name: Feature 제안을 식별하고 초안을 등록한다
      definition_ko: >-
        제안과 기존 기능의 관계를 검토하여 새 Feature와 개정의 범위를 결정한다.
        작성 기준과 대상·담당·안전 기본값의 출처를 확인하고 변경 사유를 보존한 초안을 등록한다.
      notes: []
      activity_ids: [FPW.1-A01]
      outcomes: [O1]
      evidence:
        - {work_product: WP-FEAT-REG, outcomes: [O1]}
        - {work_product: WP-REF-LINK, outcomes: [O1]}
```

`definition_ko`는 원문 업무 정의, `notes`는 적용 예·경계·관련 절차를 설명하는 참고다. `outcomes`는 해당 프로세스의 O1..On, `activity_ids`는 실제 기존 활동 키, `evidence`는 해당 BP의 결과를 확인할 WP와 성과의 명시적인 연결이다. 활동별로 출력이 없던 코드 검사·저장소 관리 등은 실제 결과 기록을 식별하는 WP를 보강한다. 표에서 연결을 보여주는 것은 내용의 승인이나 실제 수행 완료를 뜻하지 않는다.

공통 `reference_model`은 모델 ID·버전·소유 주체·업무 범위·참고 문헌(공식 공개 URL)·정의 상태를 담는다. 로컬 PDF의 전체 경로/해시는 내부 분석 문서에만 두고 브라우저 런타임에는 넣지 않는다. 기존 JSON schema1은 호환되는 추가 필드로 유지하고 계약 타입의 BP 층은 이전 fixture를 읽을 수 있도록 선택 필드로 둔다. 현재 YAML 원천에는 모든 프로세스의 BP와 성과 근거를 검증한다.

## 생성과 검증

1. `common.yaml`과 프로세스 YAML의 의미를 작성한다. 현재97활동과 기존 WP/역할 ID를 기준 목록으로 보존한다.
2. `wf_model.py`에 BP 고유 ID, 같은 프로세스의 활동/성과, WP 참조, 성과별 BP/출력 근거, 활동의 BP 연결을 검증한다. 기존 RACI·직무 분리·IAM·화면 검사도 유지한다.
3. `build_json.py`, `build_md.py`, `build_html.py`가 같은 원천의 정의와 행렬을 생성한다. `workflow-sync.ts`는 전체 문서를 정상 생성하며 작은 첫 화면 색인에는 상세 BP 본문을 싣지 않는다.
4. contracts의 WorkflowProcess에 BP 타입을 추가하고, 조회용 추적 도우미는 읽기 함수로 제공한다. backend workflow-index의 기존 진행 키·권한 구조는 유지한다.
5. UI는 기존 지연 로더로 데이터를 읽는다. 새 레퍼런스 조회와 기존 실행 흐름을 나누되 같은 프로세스·활동·WP를 가리킨다. 새 모델에도 실제 권한 외의 실행 버튼을 만들지 않는다.

출력 근거 표는 activity.outputs와 outcome의 무조건 곱으로 채우지 않고 원천 evidence 연결만 표시한다. 프로세스 간 WP 연결은 의존/인계의 근거이며, 그것만으로 전체 프로세스가 반드시 일렬로 수행된다고 표시하지 않는다.

## 업무 범위 보강

기존 FPW.1~14를 보존하며 다음 지원 영역을 별도 정의한다. 이는 새로운 인사·재무 조직 전체를 추정하는 것이 아니라 현재14부서와 현재 플랫폼의 업무 범위를 보강하는 것이다.

| 영역 | 기존 공백/근거 | 주요 책임 |
| --- | --- | --- |
| 개발비·원가 기준 | 산정 CRUD/체크/전이/기준 발행·실적 API와 역할4개가 있지만 절차 활동 없음 | 원가 기준 관리자·산정 작성/승인/열람자 |
| 접근·운영·복구 | R-SYS의 계정 상태/소유자 이관 권한은 있으나 절차 활동 없음. 인프라 운영은 외부 수행과 구분 필요 | 시스템관리·PKI·보안·품질·운영 |
| 기준정보·공유자산·연계 품질 | 사양/UPG/SW 구조/EO/공유자산/사전점검/동기화 화면의 업무와 인계 부족 | PLM·아키텍트·통합 |
| 데이터 분석·상품 개선 | 데이터 분석실/체험 전환/운영 데이터의 목적·품질·접근·개선 인계 부족 | 상품기획·운영·DPO·법무·품질 |

기존 FPW.8에는 정책 되돌리기의 복구 기준 검증/독립 승인/실행과 재시도·차량 적용 수렴을 추가한다. 긴급 차단 복원은 차단 해제(INACTIVE)이며 별도의 정상 활성화 조건을 통과해야 ACTIVE가 된다는 경계를 명확히 한다. 안전 등급이나 승인 기준을 바꾸는 작업은 아니다.

## 화면 구조

허브의 레퍼런스 조회에서14부서를 역할 전환 없이 비교하고 프로세스 시트로 이동한다. 시트는 식별 정보·Purpose·번호 있는 Outcomes·BP별 정의/Note/입출력/RACI/연결 활동·두 성과 행렬·프로세스 간 인계 순서로 읽힌다. 기존 흐름도·활동 카드·WP 상세는 계속 사용할 수 있다. 기존 활동 링크의 키는 그대로이며 연결한 BP와 양방향으로 이동한다.

기존 SUIT·플랫폼 토큰을 유지한다. 본문 폭은 읽기 길이를 제한하고, 넓은 화면은 문서 탐색+시트, 390px은 한 열을 사용한다. 행렬은 독립 스크롤/열 머리/행 머리를 갖추며 완료·정의·성과를 색만으로 구분하지 않는다. 1366/390의 실제 내용 렌더, 취소·뒤로·직접 URL, 역할/진행 상태 불변을 검증한다.
