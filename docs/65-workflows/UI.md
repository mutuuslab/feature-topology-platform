# 업무 절차 ↔ 플랫폼 UI — 일이 되게 하는 연결

이 문서는 `docs/65-workflows`의 절차 모델을 **플랫폼 화면에서 실제 업무로 수행하는 방법**을 정한다.
모델은 `model/*.yaml`이 단일 소스이고, `out/workflows.json` → `FF/contracts/src/generated/workflows.ts`로 동기화된다.
UI는 그 데이터를 **그대로** 읽는다(별도 표를 만들지 않는다).

## 업무 건·산출물 실행 기능 (2026-11-08)

`/procedures/work`는 업무 대상마다 독립된 건을 만들고, 모델의124활동·122WP에 맞는 내용을 작성·개정·검토·인계하는 실행 화면이다. 이전의 전역 활동 완료 체크는 대상별 업무 처리나 원천 승인 완료의 근거가 아니다.

- 수행·책임(R/A) 역할만 작성·제출한다. 필수 WP의 모든 내용과 근거 또는 실제 첨부가 있어야 제출할 수 있다. 이전 활동의 수락과 받은 인계의 인수가 선행 조건이다.
- 업무 건 버전이 달라지면412로 거부한다. 입력 초안은 활동·WP별로 보존하고 최신 기록과 대조한 뒤 다시 제출한다.
- 제출자·산출물 작성자는 자기 결과를 독립 검토할 수 없다. 수락한 버전은 보존하고, 보완 요청된 산출물만 새 버전으로 작성한다. 이 검토 수락은 안전/Gate/정책/출시 승인 권한을 주지 않는다.
- 인계 요청은 실제 모델의 다음 활동으로만 보낸다. 같은 요청 번호·본문의 재시도는 기존 인계로 응답하며, 다음 담당자가 의견을 적고 인수 또는 반송해야 끝난다. 발신자는 자기 인계를 인수할 수 없다.
- 앞 활동과 다음 활동의 수행 역할이 다르면 실제 인수 기록 없이는 다음 활동의 독립 검토를 제출할 수 없다. 이벤트 저장 실패 때는 업무 건·인계·성공 이력을 함께 롤백하고 실패 감사를 별도로 남긴다.
- 기본 IAM 역할이 없는 조직 역할은 SYSTEM_ADMIN이 확인된 ACTIVE 실제 계정에 구체적으로 배정한다. 부서 선택으로 권한이 생기지 않으며, 철회 후에는 진행 중인 건도 해당 역할로 변경하지 못한다.
- 소형 첨부는 파일 최대3개이며 작성 내용·base64 첨부·메타데이터를 합친 한 요청이96KiB 이하여야 한다. 전역 HTTP 기본100kb 한도는 변경하지 않는다. 서버가 실제 업로드 bytes의 SHA-256을 계산한다. 큰 PDF·시험 산출물 전체 업로드는 이 기능만으로 지원 완료가 아니다.
- FEAT-id@version 대상은 실제 저장된 Feature/Gate/Evidence/분석/정책/Baseline의 레코드·버전·내용 해시를 조회한다. ALM/P13 원천은 해당 도메인 통합 후 사용할 수 있다. `RESOLVED`는 저장 레코드 관측이며 외부 파일 존재·무결성·개인 서명·원천 승인 유효성 검증을 뜻하지 않는다. 알 수 없는 대상·URL 입력은 `DECLARED`(원천 미확보)다. 정본 관측 JSON은 실제 근거 파일로 첨부할 수 있으며 제출 조건은 유지한다.

부서 메뉴는 주 업무와 참조 업무를 각각 개발비 산정·협력사 납품/검수·검토/협의·Feature 기획/정의 등 실제 경로 성격으로 분류한다. 기존 RACI와 경로는 보존한다. 부서 공통 대시보드와 역할 기본 대시보드 진입도 제공한다.

추적·개인정보·키/보안·현장/출하·운영 데이터도 각각 분류하며, Baseline/Variant/검증 화면을 외부 연계로 잘못 묶지 않는다. 업무 건을 열면 현재 역할의 수행·책임 활동을 먼저 선택하고, 미배정·검토 중·수락된 산출물 입력은 읽기 전용이다. 목록에서 검토 대기·수락·인수 대기 수를 확인할 수 있다.

18개 절차 흐름도는 실제 직교 경로를 평가해 역할 레인·동일 단계 문서·병렬 행만 재배치한다. 활동·RACI·간선과 입력/산출 레인은 보존하며, 교차 수331→250·기존 상한250·겹침0·경로/결정성 검사를 통과해야 한다.

원천별124활동/122WP 소스 위치와 미수락 조건은 `node FF/tools/workflow-implementation-audit.ts`로 생성하는 `out/implementation-coverage.json`에 기록한다. route·화면 존재나 일반 업무 건의 수락을 native 업무 구현 완료로 계산하지 않는다. 남은 완료 조건은 핵심 활동별 정본 binding/도메인 Guard/WP 시험, 큰 산출물의 검증 가능한 보관 연결, ALM/P13 통합 회귀, 각 팀 및 전체 이해관계자 하네스 리뷰와 개선·재검증이다. 이 조건 전에는 전체 완료나 게시 완료로 판정하지 않는다.

## 활동 상세가 보여 주는 것 (모델 필드 그대로)

- **RACI**: 수행(R)·책임(A)·협의(C)·통보(I), 내 역할 배지
- **시작 조건·Gate 판정**: `trigger`, `gateDecision`
- **이 활동이 보장하는 결과**: `outcomes` → 프로세스 `outcomes.text`
- **단계·완료 기준**: `steps`, `checks`
- **입력·산출 산출물**: `inputs`/`outputs` → 프로세스 `workProducts`의 이름·키
- **플랫폼 action·Gate**: `platform.actions`, `platform.gates` (기술 식별자 그대로)
- **화면 입력·버튼**: `platform.ui.fields`/`buttons` — 필드 이름(`name=`)·버튼(`data-ui=`) 그대로
- **SLA**: `sla_hours` — 앞 활동이 끝난 뒤 완료까지 허용 시간
- **플랫폼에서 하는 곳**: `platform.screens` → 실제 라우트 링크
- **다음 활동**: `next` → 같은 절차의 다음 활동 링크
- **기존 진행 표시**: 서버 또는 브라우저 시연 데이터에 체크 상태·Evidence 참조·선택 서명을 저장한다. 이는 대상별 실제 업무 처리나 원천 Gate·정책·안전 승인의 완료 근거가 아니다. 실제 건·산출물 처리는 `/procedures/work`, 도메인 승인은 원천 기능에서 수행한다.

## 일이 되게 하는 규칙

1. **내 역할 우선**: 화면 패널은 R·A 활동을 먼저 보여 준다. 허브의 내 업무는 생애주기 순서다.
2. **앞 활동이 끝나야 다음 활동**: 서버 검토함과 화면이 같은 규칙(`contracts readyActivityIds`)을 쓴다.
   아직 준비되지 않은 활동은 “앞 활동 대기”로 표시하고, 완료 API도 막는다(422 GUARD_FAILED).
3. **다음 할 일**: 지금 할 수 있는 첫 활동을 큐 상단에 고정한다. 완료를 누르면 다음 활동으로 넘어간다.
4. **화면과 절차의 연결**: 활동의 `platform.screens`가 있으면 화면 링크를, 없으면 “플랫폼 화면 없음”을 보여 준다.
   화면에서 “이 화면의 업무 절차”를 열면 같은 활동 상세가 보인다.
5. **완료 기준은 문장이 아니라 확인 항목**: `checks`를 목록으로 보여 주고, 완료·Evidence·서명과 함께 남긴다.
6. **권한**: 플랫폼 action은 IAM action 이름이며, 실행은 각 화면의 권한 게이트(`usePermission`)를 따른다.
   절차 모델의 R[0] 역할과 IAM 권한의 정합성은 `check.py`가 검사한다. 활동 완료 권한은 서버가 조직 역할(R·A)로 확인한다.
   데모 신원은 `X-Actor-Id`(usr-&lt;persona&gt;)·`X-Actor-Role` 헤더이므로 실제 IAM으로 바꿀 때 이 지점을 교체한다.

## C3 — 검토함·알림 (2026-10-19)

- **검토함**: `/procedures` 상단 “내 차례” — 내가 책임(A)인 준비 활동과 기한이 지난 활동.
  활동 완료가 바뀌면 다시 읽는다. 각 항목은 절차 상세 `?a=`로 바로 연다.
- **할 일/검토/기한 초과** 수는 진행률 줄에 함께 보인다(서버 `GET /api/procedures/inbox`의 summary).
- **인계 알림**: 활동을 완료하면 다음 활동의 R·A 역할에 `PROCEDURE` 범주 알림이 간다(같은 트랜잭션).
- **SLA 초과 알림**: 60초마다 훑어 기한이 지난 준비 활동을 활동당 한 번 알린다(경고). 완료·취소하면 표시를 지운다.
- **메뉴 배지**: 업무 절차 메뉴에 할 일+검토 수를 붙인다(서버 `GET /api/procedures/summary`). 211KB 문서는 배지에 쓰지 않는다.
- **검토함 연결**: 기존 `/admin/approval`(검토함) 위에 절차 검토가 있으면 “내 차례” 요약과 업무 절차 링크를 보여 준다
  (211KB 문서 없이 요약 API만 쓴다).

## C4 — 표준 따라하기 앵커 (2026-10-19)

- 활동의 `platform.anchor`가 화면의 `data-tour`와 이어지면, 화면 패널의 **표준 따라하기**가 서랍을 닫고
  현재 화면에서 대상 요소를 스포트라이트한다(단계·확인·입력/버튼·결과를 옆 패널에 표시).
- 가이드는 `/learn` 튜토리얼과 같은 스포트라이트(`shell/spotlight.ts`)를 쓰고, 절차 데이터는 열 때만 지연 로딩한다.
- 파일럿 10개 활동에 앵커를 붙였다(Feature 등록·Variant·안전 분류·Release Sign-off·가상검증·차단 요청/승인/복구·차량 상태·Baseline 승인).
  나머지 활동은 앵커가 없으면 따라하기 버튼이 보이지 않는다 — 화면을 고치며 늘린다.
- 검증: `e2e/tests/procedures.spec.ts` — 1366에서 빠른 완료가 진행률을 바꾸고, 화면 패널의 따라하기가 서랍을 닫고
  대상에 `data-tour-active`·`.sh-spot`을 붙이는지 확인한다.

## 메인 화면 절차 지도 (2026-10-19)

- `/`의 **업무 절차 지도**는 HARA(FPW.2)를 제외한 모든 절차를 생애주기·지원 단계의 가로 흐름으로 보여 준다(2026-11-04 기준 전체 14개 중 13개). 각 칸은 ID·이름·Gate·완료 수,
  내 차례(할 일+검토)를 표시하고, 내 차례가 있는 첫 절차에 "다음"을 붙인다. 칸을 누르면 `/procedures/:id` 흐름도로 간다.

## 담당자 웨이브 (2026-11-05)

담당자 5명 E2E 점검(상품기획·시스템엔지니어링·기능안전·운영관제·Feature DB 관리)에서 나온 막다른 길을 화면·모델 양쪽에서 막았다.

- **협의(C)·통보(I) 활동의 실행**: 검토 포털의 '협의 요청' 한 건(대상·요청 부서·기한·살펴볼 것)으로 실행한다. 포털 부서는 동의·보완·반대 + 메모로 답하고, 요청 부서 홈과 감사(`CONSULT_REQUEST`·`CONSULT_OPINION`)에 남는다. 요청자는 자기 요청에 의견을 낼 수 없다. 데모의 포털 세 부서(구매·법무·개인정보)는 viewer 계정에서 '담당 부서'를 골라 체험한다. SSO에서는 요청 본문의 부서 값을 신원으로 인정하지 않으며, 신뢰할 수 있는 회사 계정의 부서 신원 연계가 마련될 때까지 협의 요청·의견 쓰기를 403으로 거부하고 거부 감사를 남긴다. SSO 부서 신원 연계는 남은 일이다.
- **검토함**: 부서별로 맡은 대기열을 급한 순서로 보인다 — 긴급 차단·복원의 남은 기한 → 사후 검토 → Gate → 승인·확정 → 분류. 요청 시각·요청자 이름·기한도 함께 보인다.

- 자동화하지 않은 것: 다이얼로그 포커스 복귀(UX-14), 다이어그램 라벨 겹침(UX-12), 반투명 레이어 대비 합성(axe로 대체).
- 산출물: `out/_uiux/uiux_audit_*.json|md`(로컬·라이브 실행).
