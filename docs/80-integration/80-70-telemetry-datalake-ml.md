# 차량 텔레메트리 → Data Lake → 분석·학습 → 플랫폼 판단 (설계)

> 사용자 요청(2026-10-18): "Telemetry는 현대자동차 Data Lake와 인터페이스가 되어야 한다. 차량 데이터를 텔레메트리로 받아서 분석·학습해야 한다. 설계해."
> 현재: 플랫폼은 차량 보고(상태 보고 v2·회신·고장, IF-06)를 직접 받는다. Data Lake·스트림·학습은 없다. IF-03(DW/DM)은 모의 대사뿐, 실험 효과는 모의값이다.

> 경계(2026-10-18 사용자 지적 "Data Lake도 외부 시스템 — 우리가 설계하지만 FF Platform과 서버가 다르다")
> - Data Lake는 우리가 설계하지만 **별도 서버·별도 저장소·별도 배포·별도 소유 조직**이다.
> - FF는 GitLab·JIRA·codeBeamer와 같은 방식으로, 외부 연계 **IF-15 "차량 데이터 Data Lake"**로만 붙는다.
> - FF 안에는 Lake의 코드·저장소·학습을 두지 않는다.
> - 구현 항목은 [`FF/BACKLOG.md`](../../FF/BACKLOG.md) 텔레메트리 절에 있고, UI/UX가 먼저다.

> **Lake 서버 v1 설계(2026-10-24, 사용자 결정 "OTA처럼 별도 서버로")**: [80-75 Data Lake 서버 — 간단 설계](80-75-data-lake-server.md) · 계약 [`datalake-if15.openapi.json`](datalake-if15.openapi.json) · 이벤트 스키마 [`datalake-if15/`](datalake-if15/).
> - v1은 **차량 → FF → Lake**로 시작한다(FF가 검증해 받은 제어 채널 자료만). 이 문서의 차량 직송 데이터 채널(§2)은 3단계 목표로 남는다.
> - 이 문서와 다르게 정한 것(Kafka 대신 HTTPS 묶음, 설치마다 Lake 하나·CN 기본 제외, 보안은 경보만 등)은 80-75 0장 표 C1~C6에 있다.

## 0. 시스템 경계와 주인 규칙
| 시스템 | 서버 | 하는 일 |
|---|---|---|
| FF Platform | 지금 서버(개발: backend 9101·frontend 9012) | Feature·정책·서명 배포·단계 확대·긴급 차단·감사, 제어 채널(상태 보고) 수신 |
| Data Lake | **별도 서버**(개발: repo 안 별도 workspace `datalake/`, 포트 9301, 자체 저장소) | 데이터 채널 수신, Bronze·Silver·Gold, 데이터 계약·신선도, 학습·모델 레지스트리·모델 카드 |

- FF ↔ Lake 연결은 **IF-15** 하나다.
  - 소속은 D05-01 API Gateway다.
  - 사용처는 D04-03 운영 데이터 수집, D06-12 이상 징후, D01-07 실험이다.
  - 어댑터는 mock(fixture)과 live(HTTP·Kafka)이고, `IF_MODE_15`로 고른다.
- 차량 → Lake 데이터 채널은 **FF를 거치지 않는다**. FF가 직접 받는 것은 지금처럼 제어 채널뿐이다.
- 주인 규칙(ext-sync `SYNC_OWNERSHIP`과 같은 방식)

  | 사실 | 주인 | 반대쪽이 하는 일 |
  |---|---|---|
  | 차량 원천, Bronze·Silver·Gold, 데이터 계약, 신선도 | Lake | FF는 읽기만 한다. 신선도 초과면 그 지표로 내리는 판단을 HOLD한다 |
  | 모델 학습·평가·레지스트리·모델 카드·드리프트 | Lake(학습 조직이 모델 승인) | FF는 "어느 모델 버전의 점수를 판단 화면에 쓸지" **사용 승인**만 한다(2인·직무 분리·감사) |
  | 이상 징후 판정, 단계 확대·차단·롤백, 실험 배정, 수집 정책 서명 배포 | FF | Lake는 라벨(CDC)로 받는다 |
  | 사람 판정(확인·오탐) | FF | Lake는 재학습 라벨로 받는다 |

## 1. 원칙
1. **원장 분리**
   - 차량 원천 데이터의 원장은 Data Lake다.
   - 플랫폼은 원천을 저장하지 않는다. 판단에 필요한 집계·안전 이벤트·모델 점수만 받는다(961만 대, 개인정보, 보존·현지화).
2. **양방향 라벨**
   - 플랫폼은 "어느 차량이 언제 어떤 Feature 버전·Flag·단계·실험군이었는지"를 Data Lake에 보낸다.
   - 이 라벨이 없으면 차량 데이터를 Feature 기준으로 분석·학습할 수 없다.
3. **ML은 권고, 판단은 규칙·사람**
   - ISO 26262·SOTIF(ISO 21448)·ISO/PAS 8800(AI 안전) 기준으로, 모델 점수가 단계 확대나 긴급 차단을 자동 실행하지 않는다.
   - 자동으로 막는 것은 통계 규칙(사전 등록된 임계·신선도)뿐이고 fail-closed다.
   - 모델 점수는 Evidence로 붙고, 결정은 기존 2인 승인 경로를 탄다.
4. **데이터가 늦으면 보류**
   - 신선도 기준(SLA)을 넘긴 지표로는 판단하지 않는다. 단계 확대를 HOLD하고 사유를 보인다.
   - 차량 판단의 보류 원칙(문맥이 없거나 오래되면 HOLD, Safe Default)과 같은 규칙이다.
5. **Closed loop — 계속 점검하고 고친다**(9장)
   - FF는 Lake에서 Feature별 데이터를 계속 받아 네 가지를 판정한다: 잘 동작하는가·문제가 있는가·개선할 것이 있는가·위험이 있는가.
   - 판정 결과는 조치로 이어진다. 조치 뒤에는 다시 데이터로 효과를 확인한다.
   - 효과가 확인되어야 닫는다. 확인되지 않으면 다시 연다.

## 2. 전체 구조
```
 차량(ECU·Feature 런타임)                     플랫폼(Feature Platform)
  ├ 상태 보고 v2 ──── 제어 채널(GLEO, IF-06/07) ──▶ 적용 상태·회신·고장(지금 그대로)
  └ 텔레메트리 로거 ── 데이터 채널(MQTT 5, mTLS) ─▶ 수집 게이트웨이 ─▶ Kafka
                                                           │
                       ┌──────────── Data Lake (시장별 리전: KR·US·EU·CN) ────────────┐
                       │ Bronze 원본(불변·서명 검증) → Silver 정제·가명화·플랫폼 라벨 조인 │
                       │ → Gold 집계(Feature·버전·코호트·5분/1시간/1일) · 피처 스토어       │
                       │ → 학습(MLOps: 데이터셋 해시·모델 레지스트리·모델 카드)            │
                       └─────────────────────────────────────────────────────────────────┘
   플랫폼 ◀── Gold 집계(5분 pull) · 안전 이벤트(스트림) · 모델 점수 · 신선도
   플랫폼 ──▶ 라벨(CDC: 정책·게시본·단계·긴급 차단·실험 배정·차량별 적용 상태) · 수집 정책
```
- **제어 채널과 데이터 채널은 분리한다.**
  - 지금의 상태 보고는 안전 근거(서명·CMAC·순번)라 제어 채널에 둔다.
  - 대용량 신호는 데이터 채널로 보낸다. 데이터 채널이 막혀도 제어는 영향받지 않는다.
- **수집 정책(Collection Policy)**
  - 어떤 신호를, 어느 차량군에서, 어떤 트리거로 모을지를 플랫폼이 정한다.
  - 수집 정책은 Flag 정책과 같은 서명 게시본 경로로 차량에 내려간다. 서명·대상·단계·감사를 재사용한다.
  - 수집 비용·동의 범위를 화면에서 미리 본다.
- **CN 처리**
  - CN 데이터는 현지 리전에서 수집·학습·집계한다.
  - 국외로는 k-익명(5대 이상) 집계와 모델 점수만 나간다(FFG-TEL-005).

| 주행 맥락 | 속도 대역, 도로 등급, 날씨·조도, ODD 이탈 | 트리거 스냅샷에 포함 | 안전 운영 | 스냅샷과 같음 | 원시 위치·운전자 신원·연락처 없음 |
| 수집 상태 | 버퍼 적재량, 전송 지연, 결측률 | 1시간 | 안전 운영 | 90일 | — |

- **원천 메시지 봉투 `TelemetryEnvelope v1`**
  - 식별·주기: vehicle_pseudonym, market, schema(id·version), seq, observed_at, received_at
  - 서명: key_epoch, signature
  - 플랫폼 라벨: labels{featureId, version, policyHash, stage, experimentArm, collectionPolicyId}
  - 내용: payload
  - 서명은 차량 키로 하고, Bronze 적재 전에 검증한다. 검증에 실패한 메시지는 격리하고 버리지 않는다.
- **데이터 계약 `DataContract`(데이터셋마다)**
  - 소유 조직, 스키마 버전, 신선도 SLA(안전 지표 10분, 사업 지표 1일), 품질 검사(결측·중복·범위), 보존, 범주, 시장
  - 계약이 깨지면 그 지표로 내리는 판단은 보류한다.

## 4. 분석·학습
| 모델 | 목적 | 입력(Gold 피처 + 플랫폼 라벨) | 기법 | 플랫폼에서 쓰는 곳 | 권한 |
|---|---|---|---|---|---|
| ① 배포 신호 검정 | 적용군과 대조군의 차이 감지 | 적용 실패율·DTC·안전 이벤트율, 코호트별 | 순차 검정(SPRT)·상대위험 신뢰구간·CUSUM — 규칙, 학습 아님 | 단계 확대 중단 기준, 이상 징후 자동 생성 | **자동 HOLD 가능**(사전 등록 임계) |
| ② 차량 단위 이상 탐지 | 개별 차량·소집단의 비정상 패턴 | 차량별 시간 창 피처(DTC 조합, 개입 빈도, 지연) | Isolation Forest / 오토인코더 | 이상 징후 후보(사람 확인 대기) | 권고 |

| ④ 체험 전환 성향 | 제안 대상 고르기 | 가명 성향 구간, 체험 중 실사용일 | 로지스틱/GBM, 공정성 점검(국가·연령대) | 체험 제안 대상 추천 | 권고 |

- **MLOps 기록**
  - 학습 데이터셋 해시(Silver/Gold 스냅샷), 코드 버전, 하이퍼파라미터, 평가(정밀도·재현율·보정·공정성), 모델 카드
  - 모델 레지스트리에 버전으로 남긴다.
- **모델 승인(Lake 쪽)**
  - 학습자 ≠ 승인자(직무 분리). 안전 용도(②③)는 Safety Manager가 확인한다.
  - 승인된 모델만 점수를 IF-15로 낸다.
- **모델 사용 승인(FF 쪽)**
  - FF는 Lake가 승인한 모델 중 "어느 버전의 점수를 판단 화면에 쓸지"만 승인한다(2인·감사).
  - 사용 승인이 없거나 드리프트 표시가 붙은 점수는 화면에 "참고 불가"로 보인다.
- **피드백 루프**
  - 사람의 판정(이상 징후 확인·오탐, 긴급 차단, 롤백, 체험 구매)이 라벨로 Data Lake에 가서 재학습에 쓰인다.
  - 오탐률·놓친 사고를 모델 카드에 갱신한다.
- **드리프트**
  - 입력 분포·성능 저하를 감시한다.
  - 기준을 넘으면 그 모델 점수를 "참고 불가"로 표시하고 재학습을 요청한다.

## 5. 플랫폼이 받는 것·보내는 것 (IF-15 — 별도 서버 간 인터페이스)
| 방향 | 무엇 | 방식 | 주기 | 실패하면 |
|---|---|---|---|---|
| Lake → 플랫폼 | Gold 집계(Feature·버전·코호트·창) | 서빙 API(REST) 또는 SQL 엔드포인트 pull | 5분(안전)·1일(사업) | 신선도 초과 → 그 지표 기반 판단 HOLD |
| Lake → 플랫폼 | 안전 이벤트(개별, 가명) | Kafka 토픽 구독 | 실시간 | 재접속·오프셋 재개, 지연 표시 |
| Lake → 플랫폼 | 모델 점수(배포별·코호트별)·모델 카드 | 서빙 API | 점수 갱신마다 | 점수 없음 = 권고 없음(판단에는 영향 없음) |
| Lake → 플랫폼 | 모집단 실측(탑재·커넥티드·SW 분포) | 일 배치 | 1일 | 마지막 값 + 경과 표시 |
| 플랫폼 → Lake | 라벨 CDC(정책·게시본·단계·긴급 차단·롤백·실험 배정·차량별 적용 상태·사람 판정) | 이벤트 이력(outbox) → Kafka | 실시간 | 보낼 함 재시도(GitLab·JIRA 연계와 같은 엔진) |
| 플랫폼 → 차량 | 수집 정책 | 서명 게시본(기존 배포 경로) | 정책 변경 시 | 차량 거부 = 회신으로 확인 |

## 6. 화면 (각 화면의 핵심 메시지는 "판단")
1. **공통 — 데이터 신선도 칩**
   - 텔레메트리 수치마다 출처(Data Lake 데이터셋), 기준 시각, 지연을 붙인다.
   - SLA를 넘으면 경고하고, 판단 보류 사유로 연결한다.
2. **정책 상세 → Canary 관측 패널**
   - 적용군과 대조군의 실패율·DTC·안전 이벤트를 중단 기준선과 함께 추이로 보인다.
   - 모델 ③의 위험 점수(권고, 상위 기여 요인)를 함께 둔다.
   - 핵심 메시지 예: "이상 없음 — 20% 확대 가능", "DTC 상대위험 1.8 — 확대 중단", "지표 23분 지연 — 확대 보류".
3. **단계 확대 Drawer — 중단 기준 설정**: 지표·임계·신뢰수준·관측 시간·신선도를 정하고 사전 등록한다(FR-ROL-002-006).
4. **Feature 상세 → '운영 지표' 탭**: 버전별 활성 차량(만 단위)·사용률·적용 실패율·DTC·배포 후 VOC·롤백 수를 보인다.
5. **이상 징후**: 출처(규칙 ①·모델 ②), 증거 스냅샷 링크(Data Lake), 사람 판정(확인·오탐)을 보인다. 판정은 재학습 라벨이 된다.
6. **안전 KPI**: Data Lake 실측으로 바꾼다. 임계를 넘으면 이상 징후 건과 연결한다.
7. **실험**: 모의값을 실측 효과로 바꾸고, 신뢰구간·표본 수를 보인다. 표본이 부족하면 "아직 판단 불가".
8. **체험 분석**: 실사용일과 구매 전환의 관계, 모델 ④ 추천 대상(공정성 점검 결과 포함)을 보인다.
9. **새 화면 '수집 정책'**: 신호·대상 차량군·트리거·범주·동의 근거·예상 데이터량(일 GB)·시장을 보인다. 서명 배포·회신으로 적용을 확인한다.
10. **새 화면 'Data Lake 연계'** (외부 시스템 화면 — Lake의 내용을 FF가 읽어 보여 줌)
    - 데이터 계약(신선도·품질·최근 적재)
    - 모델 목록(Lake 소유: 버전·평가·드리프트)과 FF 사용 승인
    - 라벨 보내기 현황
    - 사용 승인은 검토함 '내 차례'로 들어간다.
11. **데이터 거버넌스**: 받는 데이터마다 근거(동의·법령)·보존·가명 처리, 보내는 라벨 목록, CN 국외 이전 보류를 보인다.

## 9. 지속 점검·개선 Closed loop (2026-10-18 사용자 요청 "Data Lake에서 Feature 관련 데이터를 받아 잘 동작하는지·문제·개선·Risk를 계속 분석하고 개선 loop — 계속 모니터링하면서 Closed loop")
```
   ┌──────────────── Data Lake (별도 서버) ────────────────┐
   │ Feature별 Gold 집계 · 안전 이벤트 · 모델 점수 · 신선도 │◀──────────── 라벨(조치·판정·효과) ──┐
   └──────────────────────────┬────────────────────────────┘                                    │
                              │ IF-15                                                            │
   FF ① 관측 → ② 판정(4축) → ③ 점검 결과(Finding) → ④ 조치 → ⑤ 효과 확인 → 닫기 / 다시 열기 ───┘
                                                    │
                                     JIRA 개선·결함 · codeBeamer 요구 변경 · 정책 HOLD·롤백·차단
```
### 9.1 판정 4축 (Feature 버전마다)
| 축 | 질문 | 근거 지표(Lake Gold, 예) | 판정 주체 |
|---|---|---|---|
| 동작 | 의도대로 켜지고 쓰이는가 | 적용 성공률, 적용 지연, 상태 전이 실패, 차량 회신 불일치 | 규칙 |
| 문제 | 고장·안전 이벤트가 늘었는가 | DTC·ECU 리셋·AEB/ESC 개입·운전자 개입의 적용군 대 대조군 상대위험, VOC | 규칙 ① + 모델 ②(권고) |
| 개선 | 더 좋게 만들 여지가 있는가 | 사용률 저하·수동 끄기 비율·체험 후 미전환·특정 차종/시장 편차·ODD 이탈 빈도 | 분석(Lake) + 사람 |
| 위험 | 앞으로 문제가 될 징조인가 | 추세 상승(CUSUM)·드리프트·배포 위험 점수(모델 ③)·SW 조합 편차·인증서 만료·데이터 결측 | 규칙 + 모델(권고) |

- 각 축의 상태는 `정상 · 주의 · 조치 필요 · 판단 불가(데이터 부족·지연)`다.
- `판단 불가`는 정상으로 보지 않는다. 화면에서 따로 보인다.

### 9.2 주기
| 주기 | 무엇 |
|---|---|
| 실시간 | 안전 이벤트 → 규칙 ① → 자동 HOLD 또는 이상 징후 |
| 5분 | Canary·단계 확대 중인 정책의 중단 기준 판정 |
| 1일 | 운영 중인 모든 Feature 버전의 4축 판정 → 점검 결과 생성·갱신 |
| 1주 | 개선 축 검토(담당자 회의용 요약), 열린 점검 결과의 기한 확인 |
| 릴리스·Retirement 전 | 해당 Feature의 4축 이력이 근거로 붙는다(Release Sign-off·Flag Retirement 승인 화면) |

### 9.3 점검 결과(Finding)와 상태
- `감지 → 분석 중 → 조치 중 → 효과 확인 중 → 닫힘`. 효과가 없으면 `다시 열림`으로 간다.
- 기록 내용
  - Feature·버전·축·근거(지표 스냅샷·데이터셋·기준 시각)
  - 담당 역할·기한
  - 조치 링크·효과 기준(무엇이 얼마나 좋아지면 닫는지)
  - 효과 판정(조치 전후 비교, 표본 수·신뢰구간)
- 조치 종류는 기존 연계를 재사용한다.
  - 문제·위험
    - 정책 HOLD·롤백·긴급 차단(기존 2인 승인)
    - JIRA 결함(IF-14)
    - codeBeamer 요구 재검토(IF-01, G2 재검토 표시)
  - 개선
    - JIRA 개선 이슈 → 새 Feature 버전·정책 변경 요청 → GitLab MR(IF-13)
    - 수집 정책 변경(근거 데이터가 부족할 때)
- 조치·판정·효과 결과는 라벨로 Lake에 간다. 재학습과 다음 분석에 쓰인다. 이것으로 고리가 닫힌다.
- 같은 Feature·축·원인으로 다시 감지되면 새 건을 만들지 않는다. 이전 건을 다시 연다(반복 문제 표시).

### 9.4 규칙
- 자동으로 실행하는 것은 안전 쪽 동작뿐이다: 규칙 ①·신선도 초과에 따른 HOLD.
- 롤백·차단·개선은 사람이 승인한다. 모델 점수는 근거(Evidence)로만 쓴다.
- 효과 확인 없이 닫을 수 없다. 예외(Feature Retirement 등)는 사유와 2인 승인이 필요하다.
- 불변식

  - INV-21: 기한이 지난 `조치 필요`가 담당자 검토함에 없는 경우 0
